# Frugal V1 — Technical Concept and Proposed Architecture

## 1. Overview

Frugal is a proposed AI-driven cybersecurity defence system built around two connected capabilities:

1. Continuously assessing and improving the security of the infrastructure it protects.
2. Recursively improving its own defensive capabilities.

The central idea is that Frugal should not simply identify vulnerabilities and respond to threats using a fixed set of security tools. It should also be capable of identifying limitations in those tools, developing improvements, testing those improvements and adopting verified changes.

For Version 1, we propose focusing on **tool-level recursive self-improvement**, rather than allowing the system to rewrite its own core source code or architecture.

## 2. Core Architecture: IGM and IEM

The proposed improvement process consists of two major components.

### A. Improvement Generation Mechanism (IGM)

The IGM is responsible for identifying weaknesses in Frugal's existing defensive capabilities and developing potential solutions.

Its responsibilities include:

- Analysing vulnerabilities, missed threats, false positives and unsuccessful investigations.
- Identifying limitations in existing security tools and detection methods.
- Researching possible solutions and alternative approaches.
- Modifying existing tools or developing new security tools.
- Preparing proposed improvements for testing.

For example, suppose Frugal has a tool that monitors SSH authentication attempts. The tool detects repeated failed logins from a single IP address but misses an attack distributed across several IP addresses targeting the same account.

The IGM analyses this limitation and develops an improved detection method that correlates authentication attempts across different IP addresses, accounts and time periods.

The IGM does not decide whether its improvement is successful. It only generates a candidate improvement and submits it for independent evaluation.

### B. Improvement Evaluation Mechanism (IEM)

The IEM is responsible for independently testing and validating improvements generated by the IGM.

Its purpose is to prevent Frugal from adopting changes simply because its AI believes they are better.

The IEM evaluates improvements against two categories of tests:

**1. Protected evaluation standards**

These are permanent evaluation requirements that Frugal cannot independently weaken or redefine. They include established test cases, regression tests and mandatory reliability and safety requirements.

**2. Adaptive evaluation standards**

These are additional tests that Frugal can propose as it encounters new threats, discovers new weaknesses or identifies gaps in its existing testing capabilities.

For example, if Frugal discovers that its SSH detection tool cannot identify distributed login attempts, the IEM can incorporate new scenarios into its adaptive test suite to evaluate whether future improvements can detect that behaviour.

An improvement must satisfy both the protected standards and the applicable adaptive tests before it can be adopted.

The IEM evaluates factors such as:

- Detection effectiveness.
- False-positive and false-negative rates.
- Reliability and consistency.
- Execution time and resource consumption.
- Regression: whether the improvement breaks existing functionality.
- Performance against previously unseen test scenarios.

An improvement that performs better in one area but introduces unacceptable weaknesses or instability should be rejected.

## 3. Proposed Frugal V1 Improvement Flow

The proposed prototype follows this cycle:

**Step 1 — Infrastructure monitoring**

Frugal monitors the protected environment using its available security tools. It collects relevant system logs, events, vulnerabilities and security findings.

**Step 2 — Identify an improvement opportunity**

An improvement opportunity can arise in two ways:

- Failure-driven: Frugal misses an attack, identifies a vulnerability it could not detect, produces a false positive or performs an ineffective investigation.
- Proactive: Frugal deliberately tests its defensive capabilities through authorised security simulations in an isolated environment and discovers weaknesses before they are exploited.

**Step 3 — IGM analyses the weakness**

The IGM receives the identified problem, examines the existing tool or method, investigates the likely cause and develops one or more candidate improvements.

**Step 4 — IEM evaluates the candidates**

The IEM takes the candidate improvements and tests them against controlled scenarios, the protected benchmarks, adaptive tests and regression tests.

Where possible, the old and improved versions are tested against the same scenarios so their performance can be compared.

**Step 5 — Adoption or rejection**

If a candidate satisfies the required evaluation criteria, it can be approved for deployment. Otherwise, it is rejected and the failure information is returned to the improvement process for further analysis.

For V1, deployment should be controlled, with human approval available before changes affect production infrastructure.

**Step 6 — Continuous reassessment**

After adoption, Frugal monitors the performance of the improved tool. New findings, failures and testing results become inputs into the next improvement cycle.

This creates a continuous process in which Frugal progressively improves its defensive tools and methods.

## 5. What Makes This Recursive Self-Improvement?

The important distinction is that Frugal is not only learning from security incidents.

It is improving the tools and methods it uses to perform cybersecurity defence, then evaluating whether those improvements actually make it more capable.

For example:

- First, Frugal improves its ability to detect suspicious SSH authentication activity.
- Later, it discovers that its detection mechanism still struggles with more complex distributed attacks.
- It uses that limitation to generate another improvement.
- The IEM evaluates the new improvement against increasingly challenging scenarios.
- The cycle continues.

Over time, Frugal should become more capable of identifying its own limitations, generating solutions and evaluating those solutions.

That is the recursive element: **the system improves its defensive capabilities, and those improved capabilities help it discover and develop further improvements.**

## 6. Proposed Scope of Version 1 Prototype

We propose keeping the first prototype deliberately focused.

Frugal V1 would:

1. Operate against a controlled Linux environment or test infrastructure.
2. Integrate a limited set of existing security monitoring and vulnerability assessment tools.
3. Collect and analyse security findings.
4. Support both failure-driven and proactive improvement triggers.
5. Use an AI-driven IGM to analyse weaknesses and generate improved security tools, rules or detection methods.
6. Use an independent IEM to evaluate proposed improvements.
7. Maintain protected benchmarks alongside adaptive test scenarios.
8. Adopt only improvements that pass the required evaluation criteria.
9. Maintain version history, evaluation results and rollback capability.

The prototype would initially improve security tools, detection rules, analysis scripts and investigation workflows. It would not autonomously modify its own core source code.

## 7. Longer-Term Research Direction

If V1 demonstrates that Frugal can reliably generate, evaluate and adopt useful improvements, the research can progress towards more advanced forms of recursive self-improvement.

Potential future stages include:

- Improving how the IGM identifies and analyses weaknesses.
- Improving how the IEM evaluates candidate improvements.
- Developing more advanced security tools and interconnected defensive workflows.
- Introducing controlled code-level modifications.
- Eventually investigating whether Frugal can improve aspects of its own architecture and the mechanisms through which it performs self-improvement.

The long-term ambition is to develop a defensive system whose ability to protect infrastructure improves continuously, rather than remaining limited to the capabilities it was initially deployed with.

**The central research question for V1 is:** Can an AI-driven system reliably identify limitations in its own cybersecurity tools, generate improvements, independently evaluate those improvements and progressively increase its defensive effectiveness through repeated cycles?
